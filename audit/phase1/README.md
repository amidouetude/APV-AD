## 1. Correctif hémisphère

### Où, et pourquoi pas dans le `.py`

`notebooks/simulation_functions.py` porte l'en-tête *« Auto-generated by
02_simulation.ipynb — DO NOT EDIT MANUALLY »*, et la CI régénère le fichier
depuis le notebook puis le diffe. **Éditer le `.py` seul aurait fait échouer
la CI.** Le correctif a donc été appliqué à la cellule 2 du notebook, puis le
`.py` régénéré par la cellule d'export du notebook elle-même.

Vérification préalable : la régénération, faite sur le notebook **non modifié**,
reproduit le fichier versionné **octet pour octet**. Le mécanisme est donc
fidèle, et le dépôt était bien en phase avant l'intervention.

### Le changement

Quatre lignes exécutables :

```python
# Angle of incidence on a tilted, equator-facing surface (Duffie & Beckman).
# hemisphere = +1 north (collector faces due south), -1 south (faces due north).
# np.sign() is NOT used: np.sign(0.0) == 0 would drop beta at the equator.
hemisphere = 1.0 if lat_deg >= 0 else -1.0
phi_eff_r  = lat_r - hemisphere * beta_r

cos_theta_i = np.clip(
    np.sin(dec_r) * np.sin(phi_eff_r)
    + np.cos(dec_r) * np.cos(ha_r) * np.cos(phi_eff_r),
    0, 1
)
```

`np.sign()` est écarté explicitement : `np.sign(0.0)` vaut 0, ce qui annulerait
`beta` à la latitude nulle. Le bug avait été trouvé **dans le correctif proposé**
lors de la phase 0, avant d'être écrit.

Convention retenue et testée : `lat >= 0` → hémisphère nord. À l'équateur exact
les deux orientations sont équivalentes sur une année par symétrie ; le choix
est donc arbitraire, mais il est explicite et couvert par un test de continuité.

### Ce qui n'a pas été touché

`compute_shading` : la phase 0 a mesuré que `F_shad` est identique au bit près
dans les deux hémisphères. La formule n'utilise que l'élévation solaire ;
`delta_gamma = 0` est inerte. Aucune modification.

## 2. Isolation des requêtes

### Le mécanisme remplacé

L'ancien code écrivait le site dans le dictionnaire partagé `config_00.SITES`
puis le retirait dans un `finally`. La clé forgée par `api.py`,
`f"_runtime_{lat}_{lon}"`, ne dépend **que des coordonnées**, alors que le
dictionnaire de site dépend aussi de la culture et de `borrow_from`.

### Le nouveau mécanisme

`config_00.SITES` devient un `_SiteRegistry` : le catalogue partagé reste en
lecture seule, et chaque requête reçoit une **surcouche portée par
`contextvars`**. Les threads n'héritent pas du contexte et chaque tâche asyncio
porte le sien, donc FastAPI isole les requêtes que l'endpoint soit synchrone
(pool de threads) ou asynchrone.

**Piège traité** : `simulation_functions.py` fait
`from config_00 import SITES`, il détient donc sa **propre** référence au
dictionnaire d'origine. Rebinder `config_00.SITES` seul aurait laissé le
pipeline lire l'ancien objet et la surcouche aurait été silencieusement
ignorée. `sim.SITES` est rebindé sur le même objet, et un test le vérifie.

### Avant / après, même protocole

| Scénario | Avant | Après |
|---|---|---|
| mêmes coordonnées, cultures ≠ | 0 correct / 11 `KeyError` / 1 contaminé | **24 correct / 0 / 0** |
| mêmes coordonnées, identiques | 1 correct / 9 `KeyError` | **10 correct / 0** |
| coordonnées ≠ (témoin) | 8 correct | 8 correct |

`optimizer.py` et `pareto.py` utilisent le même contexte. `api.py` renvoie
désormais un **422 explicite** au lieu d'un `KeyError` remontant en 500, et les
jobs de fond distinguent `error_kind: configuration` de `internal`.

## 3. Sémantique des bornes d'inclinaison

`config_00.py` gagne une section documentant les trois grandeurs que
`min_beta_deg` confondait :

- `beta_opt_radiative` — maximise le POA annuel. Grandeur **physique**.
- `beta_min_operational` — plancher d'**exploitation** : évacuation de l'eau,
  auto-nettoyage (poussières, harmattan), tenue structurelle, maintenance.
  C'est ce que `min_beta_deg` encode réellement.
- `beta_used` — le maximum des trois contraintes.

Avec le rappel mesuré : la borne est saturante de −7,5° à +22,5° de latitude,
les quatre sites publiés y convergent, et la pénalité énergétique reste
modeste (−3,9 % de POA au maximum). **L'inclinaison rapportée pour un site
équatorial n'est pas une recommandation issue de la physique** — c'est le
plancher d'exploitation. À faire remonter dans l'interface et dans le texte.

Aucune valeur numérique n'a été changée : la documentation seule.

## 4. Limitation documentée : pas de rangées est-ouest

Inscrite dans la docstring de `compute_POA` : l'azimut de surface n'est pas un
paramètre libre, seules les rangées tournées vers l'équateur sont
représentables. Les rangées est-ouest — configuration agrivoltaïque réelle —
exigeraient la forme complète de Duffie & Beckman avec un argument
`surface_azimuth` explicite.

## 5. Un bug de CI révélé au passage

Le job `notebook-export-drift-check` exécutait les cellules du notebook par
`exec(src, namespace)`, puis appelait `inspect.getsource()` sur les fonctions
obtenues. Or `exec` d'une chaîne laisse `co_filename == "<string>"` sans source
nulle part : `getsource()` lève `OSError: could not get source code`, et le job
échoue **avant même de pouvoir differ quoi que ce soit**. Le garde-fou ne
gardait rien.

Jupyter contourne cela en enregistrant chaque cellule dans `linecache`. Le
workflow fait désormais pareil. Job simulé après correctif : **exit 0**.

## 6. Ce qui reste ouvert

- **Le jumeau MATLAB porte le même bug.** `matlab/forcing/poa_irradiance.m`
  code la même forme plein sud (`sin(lat_r - beta_r)`). Inerte pour les quatre
  sites publiés, tous au nord — donc non corrigé ici, hors périmètre convenu.
  À traiter si le modèle dynamique doit servir au sud.
- **Aucune donnée australe réelle.** PVGIS reste inaccessible depuis le
  conteneur. Les tests australs sont géométriquement exacts (`pvlib` à 10⁻¹⁶)
  mais n'intègrent pas la saisonnalité réelle. À relancer depuis votre poste,
  comme convenu, maintenant que la correction est en place.
- **Optimiseur DE en hémisphère Sud** : non testé (≈ 200 s par run).
- **`JOBS` reste un dictionnaire en mémoire du processus** — sans danger en
  mono-worker, à déplacer avant tout déploiement multi-worker (phase 7).
